# Architecture

## Circuit design

`circuits/src/main.nr` proves a single leaf's inclusion in a Merkle tree and a threshold comparison, in one circuit.

**Leaf**: `Poseidon2::hash([artist_id, track_id, period_id, verified_count, salt], 5)`. Poseidon2 was chosen deliberately over Noir's stdlib `std::merkle::compute_merkle_root` helper: the stdlib version's off-circuit Pedersen parameters aren't safely reproducible in TypeScript, which would risk a silent mismatch between the on-chain root and the off-chain tree builder. Poseidon2 has an independently verified, bit-identical TypeScript implementation (`@zkpassport/poseidon2`), removing that risk.

**Threshold check**: `verified_count` and `tier_threshold` are `u64`, not `Field` — Noir's `Field` type doesn't support ordering comparisons, so the range-constrained integer type is required for `verified_count >= tier_threshold`.

**Public inputs**: `root` and `tier_threshold`, in that order. `verified_count` and every other input are private — this is the actual privacy property: a verifier learns only that a leaf under the committed root meets the threshold, never the count itself.

**Design simplification, stated explicitly**: the circuit proves inclusion of one pre-aggregated leaf (`verified_count` per artist/track/period), not per-event stream data. Per-event anonymization is a platform-side aggregation guarantee upstream of this circuit, not something the circuit re-verifies. This keeps the circuit's scope tractable within the build timeline; it is a scoping decision, not an oversight.

## Contract design

- **`CommitmentRegistry.sol`** — write-once mapping `(artistId, trackId, periodId) → Merkle root`. Write-once by design: a platform cannot silently rewrite a commitment after the fact.
- **`TierVerifier.sol`** — wraps the generated Honk verifier; checks the proof's public root against the registry's stored root for the claimed key before calling `verify()`, preventing a valid proof for one key being replayed against a different one.
- **`PayoutVault.sol`** — holds USDC, releases a fixed (admin-configured) amount per tier on a valid proof, tracks claimed `(artist, track, period, tier)` keys to prevent double payout.
- **`Verifier.sol` (`HonkVerifier`)** — generated by Barretenberg (`bb write_solidity_verifier`) from the circuit's verification key. Compiled with `--oracle_hash keccak` for cheaper on-chain verification; this must match the oracle hash used at proof-generation time or verification silently fails.

## Identity: ENSv2 Enhanced Access Control

The artist's ENSv2 name (Sepolia beta) uses a Permissioned Resolver. The platform's operating address is granted `ROLE_SET_TEXT` scoped to exactly one text key (`streamproof:commitment-root`) via `authorizeTextRoles` — not the whole name. This was verified two ways, not assumed:
- **Positive test**: the platform can write `streamproof:commitment-root`.
- **Negative test**: the same platform address attempting to write a different key (`description`) reverts.

## Known limitations / security considerations

**`PayoutVault.claimPayout` does not currently bind the caller or `recipient` to a specific artist identity.** A valid proof only proves "the prover knew a private input consistent with this public root and threshold" — it does not prove the caller is the artist that root belongs to. As written, any address holding a valid proof and its public inputs can direct the payout to any `recipient`, including itself. Recommended fix (not yet implemented): bind `artistId` to a specific on-chain address — either a dedicated `artistAddress` mapping set at registration, or resolved through the artist's ENS name — and require `msg.sender` to match before releasing funds.

**Other explicit non-goals for this build:**
- Proportional/exact royalty math (flat per-tier payout only)
- Multi-platform data aggregation
- KYC/AML, compliance tooling
- Chainlink CRE Confidential Workflow integration (different privacy primitive — TEE, not ZK — deliberately out of scope)
